# Install and update review, with a plan

**Date:** 2026-09-29
**Branch reviewed:** 0.8-metaharness (release v0.8.1 is tag 2cd752e1)
**Scope:** how WeftOS binaries reach a machine, how they are updated, why
this machine ended up with stale copies, and what to change. Review and
plan only. Nothing on the machine or in the code was modified.

## Status

- **Phase 2 (updater half), Phase 3 (restart half): implemented on
  `wt/weaver-update` (board card 630fb468).** `weaver update` verifies
  every archive against its published `.sha256` (plus `sha256.sum` when the
  manifest declares one) and `dist-manifest.json`, installs the whole
  release set together with per-binary atomic rename and full rollback,
  refuses Homebrew, cargo and dev builds with the owning channel's command,
  uses the cargo-dist receipt when present (and records the new version in
  it), supports `--check` and `--dry-run`, offers or flags the daemon
  restart through launchd/systemd via the existing `daemon_restart` host,
  and lists copies it did not touch. Tests run against a loopback mock
  release server with fake receipts and a fake daemon host.
- **Deviation from the plan:** the updater is in-tree (`update_flow.rs`,
  `update_release.rs`, `update_install.rs`), not an embedded `axoupdater`.
  It reads the same receipt and manifest, so switching to `axoupdater`
  later does not change behaviour. The single-installer spike, the
  `install-updater = true` regeneration, the `install.sh` wrapper and the
  Windows run remain open.
- **Deferred:** protocol-version integer and skew check in
  `DaemonClient::connect`; service-unit binary resolution from the install
  prefix; GitHub attestation and minisign verification of downloaded archives (sha256 is integrity only);
  end-to-end run on a clean VM against a real prerelease tag.

## 1. Summary

WeftOS has five separate ways to put binaries on a machine, three of
them write to different directories, and none of them knows about the
others. There is no single record of "what is installed here and from
where". The update paths that exist (`weaver update`, `install.sh`) each
guess a destination at run time, and the daemon is never reliably
restarted onto the new binary. The result on this machine is a `weft`
that is one release behind, shadowed and unshadowed in ways that depend
on `PATH` order.

The fix recommended below is small: make the cargo-dist shell installer
the one supported end-user channel, turn on its bundled updater, keep
Homebrew as a second channel that defers to itself, demote every other
path to "developer only", and add a `weaver doctor install` command that
reports every copy, every running daemon, and which one wins.

### 2.2 Every install path the project offers

1. **`scripts/install.sh`** (`curl | sh`). Hand-written, 253 lines.
   Downloads three archives, verifies with `gh attestation verify` when
   `gh` exists, copies to `${WEFTOS_INSTALL_DIR:-/usr/local/bin}`, uses
   sudo on failure, stops and restarts the kernel around the swap.
   Documented as "canonical" in `docs/deployment/install.md:3`.
2. **`weaver update` / `weft update`**
   (`crates/clawft-weave/src/commands/update_cmd.rs`). Hand-written
   self-update. Downloads the same three archives with `curl`, replaces
   each binary at `which <name>` (falling back to `/usr/local/bin`).
   Does not verify attestations or checksums. Does not restart the
   daemon; it prints "restart it" (`update_cmd.rs:112-114`).
3. **cargo-dist installers** attached to every release:
   `clawft-cli-installer.sh`, `clawft-weave-installer.sh`,
   `weftos-installer.sh` (plus `.ps1` and GUI variants). One installer per
   binary, each installs into `~/.cargo/bin` and writes a receipt to
   `~/.config/<app>/`. `Cargo.toml:395-455` configures cargo-dist 0.31.0
   with `installers = ["shell", "powershell", "homebrew"]` and no
   `install-updater` setting, so no `*-update` program is produced.
4. **Homebrew tap** `weave-logic-ai/homebrew-tap`. Generated by
   cargo-dist and published by `release.yml`. The tap holds four formulae
   (`clawft-cli`, `clawft-weave`, `clawft-gui-egui`, `weftos`). README
   line 311 documents `brew install weave-logic-ai/tap/clawft-cli`, which
   installs only `weft`, not `weaver`.
5. **crates.io.** `README.md:314` says `cargo install weftos`. The
   `weftos` crate on crates.io was last updated 2026-04-17, and
   `clawft-cli` does not exist there. `publish-crates.yml` is
   `workflow_dispatch` only (deliberately deferred). So `cargo install
   weftos` gives a months-old build, and there is no crates.io route to
   `weft` or `weaver` at all.
6. **cargo-binstall metadata** exists on clawft-cli
   (`crates/clawft-cli/Cargo.toml:22`) pointing at the release archives,
   with no signature configuration.
7. **From source, `scripts/build.sh install`.** Builds `weft` and
   `weaver` and installs to `~/.cargo/bin` (`build.sh:289-308`), with
   ad-hoc re-signing and a guard against dropping features. It does not
   install `weftos`. This is the developer path and it is the one that
   wrote the stale binary on this machine.
8. **Docker** (`ghcr.io/weave-logic-ai/weftos`), WASI and browser WASM
   artifacts. Separate distribution problems, out of scope here.

Documentation split: `docs/deployment/install.md` says install.sh is
canonical; `README.md` recommends brew and crates.io; the quickstart
(`docs/getting-started/quickstart.md:3`) says install from source;
`docs/guides/build.md` covers building. A newcomer sees four different
"first commands".

### 2.3 What already exists that the plan builds on

- `crates/clawft-rpc/src/version_check.rs` is only a "newer release
  exists" notice. It asks the GitHub API for the latest tag once per 24
  hours, caches to `~/.clawft/version-check.json`, and prints "Run:
  weaver update". It does not compare the CLI to the daemon and it does
  not know which channel installed the binary, so it tells a Homebrew
  user to run a command that will fight Homebrew. Called from
  `clawft-cli/src/main.rs:396` and `clawft-weave/src/main.rs:142`.
- `crates/clawft-cli/src/commands/daemon_guard.rs` is the real skew
  check. After connecting, it reads `kernel.status` → `build.sha` and
  warns once if it differs from the CLI's own `BUILD_GIT_HASH`. It is
  wired into only 7 call sites (agent daemon, status, voice among them),
  it warns but never blocks, and its remedy text says "run
  scripts/build.sh install", which is meaningless for a release user.
  It also treats `unknown` as a match, and a `-dirty` suffix as a
  different build, so a dev build always warns against a release daemon.
- The daemon already reports `version`, `sha` and `timestamp`
  (`daemon.rs:5468-5490`). No new wire fields are needed.
- cargo-dist already writes an install receipt, and this machine has one
  (`~/.config/weftos/weftos-receipt.json`: provider cargo-dist 0.31.0,
  install prefix `~/.cargo`, version 0.8.1). It is unused.

## 4. Root causes

1. **Three writers, three directories, no shared record.** `install.sh`
   writes `/usr/local/bin` (`install.sh:31`), cargo-dist and
   `build.sh install` write `~/.cargo/bin` (`build.sh:308`), and Homebrew
   writes `/opt/homebrew/bin`. Which copy runs depends on `PATH`, and
   here `/usr/local/bin` beats `~/.cargo/bin`, so a fresh `install.sh`
   run would shadow the cargo copies, while today the cargo copies win
   for `weft` and `weaver` only because `/usr/local/bin` lacks them. No
   channel writes a receipt that the others read, so none can tell it is
   creating a duplicate.
2. **Dev builds and release installs share a destination.** `build.sh
   install` overwrites `~/.cargo/bin/weft` with a `-dirty` build, which
   is where `0.8.0 (dec3b28f-dirty)` came from. Nothing later replaced it
   because the only tool that would have (`weaver update`) resolves the
   target via `which`, and decides "already latest" by comparing the
   *running* binary's version string (`update_cmd.rs:58`), so a dirty
   0.8.0 correctly sees "update available" but the nag that would prompt
   it is suppressed by the stale cache (section 3). The dev workflow is
   the largest single source of stale binaries.
3. **The update path is not an update path.** `weaver update`
   replaces three files by `which` and then prints "restart the kernel"
   (`update_cmd.rs:112`). `install.sh` restarts only if
   `weaver kernel status` succeeded, using whichever `weaver` is first on
   `PATH`, which may not be the one the daemon runs from. On this machine
   the daemon runs from a private project copy that neither tool would
   ever touch or restart. This is the "daemon binary swap" gotcha in
   memory: the running process keeps the old inode after the file is
   replaced, and nothing detects that.
4. **Two hand-written updaters duplicating a generated one.** install.sh
   and update_cmd.rs hardcode the archive-to-binary mapping and the
   platform triples, skip verification differently (install.sh attests via
   `gh` when present; update_cmd.rs does nothing), and are unaware of
   cargo-dist receipts. cargo-dist already ships an updater
   (axoupdater) that would read the receipt that already exists on this
   machine. Turning it on is one config line, and it is not enabled.
5. **Too many binaries, three installers, uneven documentation.**
   Three separate cargo-dist installers (one per binary) means a user who
   runs the `weftos` installer gets only `weftos`, which is exactly the
   state here. README, install.md and quickstart each name a different
   first command, and README's crates.io and brew instructions install
   an old build and half the tools respectively.
6. **The version nag and the skew check are disconnected and
   channel-blind.** `version_check.rs` tells every user to run `weaver
   update`, including Homebrew users and dev builds. `daemon_guard.rs`
   only runs on a subset of commands, only warns, and gives a
   developer-only remedy.

## 5. What well-known tools do

Findings are from each project's own documentation, fetched for this
review.

- **uv.** The standalone installer places `uv` at `~/.local/bin`, and
  `uv self update` works only for that install. "When another
  installation method is used, self-updates are disabled" and the user is
  pointed to the package manager. uv moved its installer target away from
  `~/.cargo/bin` at 0.5.0, so it no longer collides with cargo-installed
  copies. ([uv installation docs](https://docs.astral.sh/uv/getting-started/installation/))
  Distro packagers can also build uv without the self-update feature
  ([Arch packaging issue](https://gitlab.archlinux.org/archlinux/packaging/packages/uv/-/issues/5)).
- **cargo-dist and axoupdater.** cargo-dist installers write a JSON
  receipt under `~/.config/<app>` (macOS, Linux) or `%LOCALAPPDATA%\<app>`
  describing the installed version and the installer version.
  `install-updater = true` makes the shell and PowerShell installers
  bundle a standalone `<app>-update` program that reads that receipt and
  upgrades in place, and axoupdater is available as a library to embed a
  `<app> update` subcommand. It calls the unauthenticated GitHub API, so CI
  should set `AXOUPDATER_GITHUB_TOKEN`. Homebrew users keep upgrading
  through Homebrew. ([cargo-dist updater docs](https://axodotdev.github.io/cargo-dist/book/installers/updater.html),
  [axoupdater on docs.rs](https://docs.rs/crate/axoupdater/latest))
- **rustup.** One installer, proxies in `~/.cargo/bin` that dispatch to
  the selected toolchain, and `rustup self update` for itself, with an
  `auto-self-update` setting of `enable`, `disable` or `check-only`.
  ([rustup basics](https://rust-lang.github.io/rustup/basics.html))
  The relevant idea is one directory the installer owns and one command
  that updates everything it put there.
- **bun.** `bun upgrade` updates the binary in place, with `--canary` and
  `--stable` channel switches. The docs warn Homebrew and Scoop users to
  use their package manager instead to avoid conflicts.
  ([bun installation](https://bun.sh/docs/installation))
- **deno.** `deno upgrade` supports stable, lts, rc and canary channels,
  pinned versions, and an optional `--checksum=<sha256>` to verify the
  download; it uses delta patches between recent releases.
  ([deno upgrade](https://docs.deno.com/runtime/reference/cli/upgrade/))
- **gh.** Does not update itself. It prints a new-version notice and
  leaves upgrading to the package manager; the notice is disabled with
  `GH_NO_UPDATE_NOTIFIER`. ([gh environment](https://cli.github.com/manual/gh_help_environment))
- **cargo-binstall.** Verifies downloads against a minisign signature when
  the package declares `[package.metadata.binstall.signing]` with a public
  key, and its own releases use a per-release ephemeral key.
  ([binstall SIGNING.md](https://github.com/cargo-bins/cargo-binstall/blob/v1.6.5/SIGNING.md))

The pattern common to uv, bun, gh and axoupdater: an updater exists only
for the channel that installed it, other channels defer to their package
manager, and the notice tells you which command to run for *your*
channel. That requires knowing the channel, which needs a receipt.

Not verified in this review: launchd and systemd restart-on-upgrade
practices are described here from general operating-system behavior
(`launchctl kickstart -k`, `systemctl restart`), not from a cited source.

## 6. Target design

One recommended approach.

**One end-user channel: the cargo-dist installer, with the updater turned
on.** Homebrew stays as a second, self-contained channel. Everything else
is documented as developer-only.

1. **Single installer, all binaries.** Make one dist package own the
   end-user binaries so a single installer places `weft`, `weaver` and
   `weftos` together and writes one receipt listing all three. Concretely
   this means a small meta-package or a dist `[workspace.metadata.dist]`
   package selection that groups the three; the exact cargo-dist
   mechanism needs a spike (see open decisions). The installer's output
   is one install prefix, `~/.local/bin`, following uv, not `~/.cargo/bin`
   (see next point).
2. **Move end-user installs out of `~/.cargo/bin`.** `~/.cargo/bin` is
   where `build.sh install` and `cargo install` write, and that overlap
   is root cause 2. Release installs go to `~/.local/bin` (cargo-dist
   supports a configurable install path); developer installs keep
   `~/.cargo/bin`. `doctor` then detects the collision instead of the
   user discovering it.
3. **Updater: `weaver update` becomes a thin wrapper on axoupdater.**
   Enable `install-updater`, embed the axoupdater library, and delete the
   hand-written download, extract and replace code in `update_cmd.rs` and
   the update half of `install.sh`. Behavior by receipt: no receipt
   (cargo, source, Docker): print the right command for that channel and
   exit non-zero; Homebrew receipt: print `brew upgrade`; cargo-dist
   receipt: upgrade all three binaries as a set. `install.sh` shrinks to a
   redirect to the generated `weftos-installer.sh`, kept at the same URL
   so existing `curl | sh` lines keep working.
4. **Update always finishes the job.** After swapping binaries, the
   updater reads the daemon's PID and executable path (`kernel.status`
   plus `proc_pidpath`/`/proc/<pid>/exe`), and if the daemon's version or
   sha differs from the new binary it restarts it: `launchctl kickstart
   -k` when a launchd label exists, `systemctl --user restart` when a unit
   exists, `weaver kernel stop && start` otherwise. A daemon running from a
   path the updater did not touch (like the project-local copy here) is
   reported, not restarted, with the exact command.
5. **Skew check on every daemon connection, one message, right remedy.**
   Move the `daemon_guard` call into the shared `DaemonClient::connect`
   path in `clawft-rpc` so every command gets it, compare `version` first
   and `sha` second, and select the remedy text from the receipt
   (`weaver update`, `brew upgrade`, or `scripts/build.sh install` only
   for dev builds). Warn by default; refuse with a clear error only when
   the RPC protocol changed incompatibly, which needs a protocol version
   integer in `kernel.status`.
6. **`weaver doctor install` (also reachable as `weft doctor install`).**
   Read-only. Lists every copy of `weft`, `weaver` and `weftos` found on
   `PATH` and in the standard directories, each with version, sha,
   `dirty` flag, owning channel (receipt, Homebrew cellar, cargo ledger,
   `target/` path, none) and whether it is shadowed. Lists every running
   `weaver` with its executable path and build stamp. Prints the winner
   for each name and the exact fix for each problem. This is the
   inventory in section 3 as a command.
7. **Honest nag.** `version_check.rs` keeps the 24-hour cache but reads
   the receipt to pick the message, is silent for dirty or dev builds,
   and is suppressed by the existing `WEFTOS_NO_UPDATE_CHECK`. Also cache
   the *notice*, not just the latest tag, so a stale cache never hides an
   available update (the cause in section 3).
8. **Signed manifests.** Keep the sigstore attestations already produced
   (`github-attestations = true`). Have the updater verify the archive's
   SHA-256 from the release's `dist-manifest.json` always, and the
   attestation when `gh` is available. This removes the current gap
   where `weaver update` verifies nothing. Adding minisign is optional
   and not recommended in this phase, since attestations already give
   provenance and a second key is a second thing to lose.
9. **Documentation collapses to one page.** `docs/deployment/install.md`
   becomes the only place with install commands: end-user install, update,
   uninstall, developer install. README, quickstart and build guide link
   to it and carry no install commands of their own. README's
   `cargo install weftos` line is removed until crates.io publishing is
   turned back on.

## 7. Phased plan

Phases are ordered so each one is useful alone and none requires the next.

### Phase 0. Stop the bleeding (small, no design risk)

- Rewrite the `daemon_guard` remedy text and the `version_check` message
  to name the right command for a dev build versus a release install.
- Fix the doc contradictions: one install command in README, install.md
  and quickstart; remove the crates.io line; mention that brew installs
  only `weft`, or fix the formula set in Phase 1.
- Make `build.sh install` print, at the end, any other copy of `weft` or
  `weaver` on `PATH` that it did not overwrite, and any running daemon
  whose executable path differs from the installed one.
- **Acceptance:** after `build.sh install`, a machine with a shadowing
  copy prints that copy's path and version; `weft status` against a
  daemon of a different sha prints one line with a remedy valid for the
  install type; the three docs agree; no code path other than message
  text changes.

### Phase 1. `doctor install` and receipts

- Implement `weaver doctor install` as specified in 6.6, read-only.
- Have `build.sh install` write a receipt-like marker
  (`~/.config/weftos/dev-install.json`: path, sha, timestamp) so doctor
  can tell dev installs from release installs.
- **Acceptance:** run on this machine, the output lists the seven
  binaries and two daemons in section 3, marks `~/.cargo/bin/weft` and
  `weaver` as stale dirty dev builds, marks `/usr/local/bin/weftos` as
  duplicate-shadowing, and marks the project-local daemon as a different
  path from the installed `weaver`. Exit code is non-zero when any
  problem is found. Unit tests cover PATH-order shadowing, Homebrew
  cellar detection, and receipt parsing, using fixture directories.

### Phase 2. One installer, updater enabled

- Spike (one day): confirm whether cargo-dist 0.31/0.32 can produce a
  single installer for three binaries from different crates, with an
  install-path override. If not, fall back to a workspace meta-crate
  that depends on the three and re-exports their binaries.
- Enable `install-updater = true` and embed axoupdater in
  `update_cmd.rs`; remove the hand-written download code.
- Make `install.sh` a wrapper that fetches and runs the generated
  installer, preserving `--verify`/`--no-verify` semantics.
- Carry the WEFT-593 `release.yml` hand-patch through the regeneration
  per `docs/plans/weft-462-cargo-dist.md`, Phase C. Do this on a
  throwaway branch with a prerelease tag first, as that plan requires.
- **Acceptance:** on a clean macOS arm64 VM and a clean Linux x86_64
  container, `curl -fsSL <installer> | sh` yields all three binaries at
  one path and one receipt; `weaver update` on a machine one release
  behind upgrades all three and prints the new version; `weaver update`
  on a source build refuses and names the right command; on a Homebrew
  install it prints `brew upgrade`. A prerelease tag run of `release.yml`
  completes with the installer, the updater and the manifest attached.

### Phase 3. Daemon-aware update

- Implement the restart logic in 6.4 for launchd, systemd user units and
  bare daemons, and the not-touched-path report.
- Move the skew check into `DaemonClient::connect` and add the protocol
  version integer to `kernel.status`.
- Update `scripts/com.clawft.wake.plist` and the systemd unit to resolve
  the binary from the install prefix rather than hardcoding
  `/usr/local/bin/weft`.
- **Acceptance:** with a daemon running under launchd, `weaver update`
  from one release behind ends with the daemon reporting the new
  version and sha in `kernel.status` without manual steps; with a
  daemon started by hand from another path, update completes, reports the
  daemon as not restarted, and prints the command; a CLI/daemon protocol
  mismatch fails with a clear error rather than a wire error; an
  end-to-end test covers the restart path on Linux (systemd user unit in
  CI is optional; a fake service manager is acceptable).

## 9. Open decisions for the user

1. **One installer package or three?** Recommended: one, so a user cannot
   end up with only `weftos`. Cost: a meta-crate or a dist config spike.
2. **Where release installs go.** Recommended `~/.local/bin` (uv's
   choice) to separate them from dev installs in `~/.cargo/bin`. Cost:
   existing cargo-dist users must re-run the installer; doctor can flag
   them. The alternative is to keep `~/.cargo/bin` and instead move the
   *dev* install to a separate directory such as `target/dev-bin` on
   `PATH`; that changes the developer workflow instead of the user's.
3. **Do you want dev builds on `PATH` at all?** The cleanest dev setup
   is a `PATH` entry for `target/release` in the dev shell only, never
   overwriting an install.
4. **Homebrew.** Keep as a supported channel (recommended, it is nearly
   free from cargo-dist) or drop it to reduce the surface. If kept, fix
   the "installs only `weft`" gap.
5. **crates.io.** Re-enable publishing on tags, or state that it is
   source-only until the API settles.
6. **Windows.** cargo-dist builds a Windows archive and PowerShell
   installer, but the release notes treat Windows as unverified. Decide
   whether Phase 2's acceptance includes a Windows run or defers it.
7. **Blocking on protocol mismatch.** Warn-only is the safe default; a
   hard refusal on incompatible protocol is better UX but needs the
   protocol integer maintained on every wire change.
8. **cargo-dist 0.31 to 0.32 bump.** The existing plan says never during
   a product tag cut. Phase 2 needs a regeneration anyway; confirm it is
   done as one deliberate bump on a branch.
