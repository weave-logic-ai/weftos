# ADR-103 Phase 4 implementation plan and evidence

Ticket: `0dc06c23-56a0-4718-b7d5-aefc2f05d98c` (claimed by the lead before edits).

## Plan

1. Keep the existing `project` workload, certificate, gate, chain, supervisor, readiness, and adoption path. Select an OS boundary from the registered project's `[serve] sandbox` setting at launch. An unavailable or invalid requested boundary must refuse startup; it must never silently become `logical`.
2. Apply macOS Seatbelt in a fresh, single-threaded copy of the supervisor executable, then `exec` the project kernel in that same PID. This retains the kernel's PID and process group for the existing supervisor and registration contract, while avoiding `sandbox_init` in a multithreaded daemon's `pre_exec` fork. Permit the project root, the child run directory, the parent socket, system libraries, and temporary storage; withhold the user home and other project roots.
   A sandboxed or nested child now receives `<project>/.weftos/sandbox-home` as `HOME` and `<project>/.weftos/tmp` as `TMPDIR`, both mode 0700. It does not inherit the daemon owner's HOME through the allowlisted environment.
3. Enforce nested project parentage before launch: the declared parent must be an active registered project, must have `weave.master = true`, and its canonical root must contain the child root. Refuse a child that claims an unrelated master or itself.
   A project-scoped master token may call `project.nested.register`, `project.nested.start`, and `project.nested.stop`. Registration requires an existing child `project.toml` naming the master and a canonical child root inside it; validation and manifest write share the manifest-store lock, and the user chain records an isolated registration. An owner token or literal `admin` cannot impersonate the master on these methods. At child launch, the master's `overlay.toml` is merged onto the user policy and the tightened result is signed as the child's parent policy. The nested lifecycle still supervises a project kernel, not an independent user daemon.
4. Exercise both successful launch and denied access with a fake kernel under an isolated test HOME and runtime root. Exercise nested parent refusals and a valid nested launch. Run the relevant `scripts/build.sh` checks and tests with the same isolation.

The selected driver lives in the registered user manifest, `~/.weftos/projects/<id>.toml`, under `[serve] sandbox = "seatbelt"`. A nested project's `<root>/.weftos/project.toml` sets `parent = "<master id>"`; the master project's `project.toml` sets `[weave] master = true`. A requested Seatbelt driver on a non-macOS host fails admission. An unknown driver fails manifest parsing.

## Remaining integration to finish

- The owner socket's process-group classifier alone cannot identify a child that calls `setsid` or `setpgid`. The user daemon now binds a separate `child-ipc/child.sock` in a parent-controlled directory. The supervisor places that path in `spawn.json`; Seatbelt permits that literal socket and withholds the owner socket. The child endpoint stamps every connection as `Child`, rejects RVF, and applies an exact method ceiling before bearer-token capability checks, including when a stolen owner token is presented. Shared, refresh and nested methods also require a live project token. The owner socket retains its existing CLI behavior. A strict test forks a test-owned sandboxed grandchild, calls `setsid`, and tries `auth.token.issue`, `project.revoke` and `kernel.shutdown` with literal `admin` and a test-issued owner token; it also tries the owner socket directly and through a project-root symlink. The isolated host r5 run passed both strict probes. This endpoint directory can be mounted read-only for a container, while its runtime remains separate and writable.

- Linux OpenShell/container driver and a macOS Apple `container` driver require an execution contract that preserves the actual kernel PID, signed spawn registration, parent socket and restart/adoption semantics. The current `Launcher` calls `registry().note_pid` with `Command::spawn().id()` and uses that same PID for lock identity, handshake, process-group termination and adoption. `docker run` and Apple `container run` return a client process PID; the kernel inside the container has another PID. Passing the client PID would fail the registration contract and could signal the wrong process. The implementation needs a verified container ID and host PID (or a protocol change to certify the container identity), a durable ID for adoption after daemon restart, and a stop path through the engine. Do not label a wrapper as a working driver until that contract is exercised.
- A container also cannot mount the current child run directory read-write unchanged: it contains the user-key pin, signed parent policy and single-use spawn token beside mutable socket, PID and state files. The parent socket lives in the user daemon's run root, whose wholesale bind mount would expose siblings' run files. The implementation must split parent-controlled read-only bootstrap/pin/policy/revocation mounts from writable guest runtime, provide separate host and guest endpoint paths, and use a stable per-child socket proxy through outer-daemon restarts.
- Wasmtime can run WASM workloads already; a WASM **project kernel** needs a WASI-compatible kernel entry point and the same signed project boot/parent link. The current native `weaver` binary cannot be passed to wasmtime.
- A nested WeftOS instance still needs an independent user daemon, chain, user key, port and mesh registration level. The new authenticated `project.nested.register` is a registration for a nested **project kernel**; its isolated level forbids implicit outer-mesh admission, but it does not start a full inner user daemon, verify a distinct inner user identity, propagate later master-overlay updates to a running child, or record a revocation event. Starting `--profile user` inside a project requires an explicit new runtime/home and a parent-signed configuration cap. The mesh-local protocol currently binds one user key per OS uid, so it needs an authenticated nested-instance identity model before that inner user daemon can join. `weave.master` alone never joins the mesh.
- The r5 boundary test hosts the child-only RPC handler on a test-owned listener, and the source test for allowed child methods has not run. A full user-daemon boot in an isolated HOME, with its production `daemon::run` listener and a real child registration over that path, is still needed to verify listener lifecycle and mesh/anchor integration. The test must use only test-owned runtime, chain, project and socket paths.
- Running this repository's dev kernel under the installed release user daemon is a manual integration step that must use an isolated project root and must not run in an automated test against real HOME or daemon state.

## Completion status

The worktree has a macOS Seatbelt launch path verified by the r5 host probe for file, socket, signal, trust-pin and escaped-process-group RPC restrictions. The production child socket binder is shared by `daemon::run` and the lifecycle RPC test; the r6 host run passed that test with allowed mesh bootstrap, anchor, shared and nested methods. An additional in-memory test exercises the real child RPC handler without AF_UNIX bind, but its source was added after r6 compiled and it has not run. Nested project admission, authenticated master token lifecycle, and a launch-time inherited governance cap are implemented and exercised by r6. A distinct inner user daemon, its isolated chain and mesh identity, live master governance propagation, Linux containers, macOS `container`, and WASI project kernels remain unimplemented. This is not a completed Phase 4 integration. None of the results above should be used as a sign-off for the remaining drivers or nested instance contract.
