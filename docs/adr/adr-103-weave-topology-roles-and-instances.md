## Context

The ADRs assume one daemon ("the daemon", "the chain", "the node"). The code and the ops docs went per-project in April 2026 without an ADR: socket, PID file, `node.key` and `workloads.json` follow a CWD walk-up to `.weftos/`, while `chain.rvf` and `chain.key` resolve from `WEFTOS_RUNTIME_DIR` or `~/.clawft/` (§2). Two project daemons therefore share one chain file and signing key with no lock. The mesh node id is a fresh UUID each boot, three documents disagree on the node-id hash, a lost mesh bind is non-fatal, and because `~/.weftos/` exists for other reasons the walk-up treats `$HOME` as a project. On the owner's Mac there are four `node.key` files and one `chain.key`.

The owner wants projects to run granularly, with their own chains and governance, behind a machine-level mesh service; projects inside a container-like boundary where WeftOS does lifecycle and coordination but not the project's development work; WeftOS runnable inside WeftOS; ESP32 and WASM supported; and a way for an organization to stand up a primary instance that distributes work to subordinates, with development, staging and production instances that are shaped differently.

## Decision

### Roles, not a process count (§3, §4)

WeftOS is four roles. A profile decides which roles one process holds.

| Role | Owns | Must not own |
|---|---|---|
| **Machine mesh service** | the box node key, the one mesh listener, Noise sessions, discovery, cryptographic admission and revocation, routing to local tenants, signed machine facts, a small machine journal | user or project chains, secrets, tokens, governance evaluation (it consumes verdicts from the owning user daemon) |
| **User daemon** | the user key and user chain, the ADR-102 token authority, secrets, the model/accelerator access path (ADR-101 loopback proxy), shared heavy services (embeddings, indexes, voice), the project manifest, supervision of project kernels | the mesh listener when a machine service runs |
| **Project kernel** | the project key and chain, the tighten-only governance overlay, workspace config, the project's workload catalog, the boundary around the project | a mesh listener; duplicated heavy services |
| **Leaf / client** | one provisioned identity and one role | a chain; governance (enforced by its parent) |

Profiles: full shared host (service + a user daemon per user + a kernel per active project); personal host (machine and user roles in one `weaver`, project kernels as children); single-tenant host such as a Pi, container or server (one process, all roles); ESP32 leaf; browser client (behind the gateway, ADR-102 token, ephemeral certified key); WASI (leaf or collapsed host).

### Owner decisions

- **D1 Mesh port.** Default **9489**, "the weave". Configurable (`kernel.mesh.listen`). Replaces 9470 in code and 9421 in docs. Bind address defaults: see A11.
- **D2 Machine mesh service.** Optional, **on by default**. Standalone and single-tenant installs may run it collapsed inside the user daemon; `kernel.mesh.service = off` disables it.
- **D3 User binding.** A user key is **bound** to the OS uid on first registration over a peer-credential-checked local socket (`getpeereid` / `SO_PEERCRED`). The binding is recorded in the machine journal; an admin can revoke and rebind.
- **D4 Runtime roots are machine-wide.** Machine role: `/var/lib/weftos` (state) and `/var/run/weftos` (sockets). Per-user state under `~/.weftos/` (`run/`, `projects/`, `chain/`). `~/.clawft/` becomes legacy, read for migration only. `WEFTOS_RUNTIME_DIR` remains the full-isolation override for tests, probes and nested instances.
- **D5 Project id.** A stable ULID in `<root>/.weftos/project.toml`, mirrored in `~/.weftos/projects/<id>.toml`.
- **D6 Project chain.** In-tree at `<root>/.weftos/chain/` (gitignored), anchored into the user chain with `project.anchor` events and subscribable by others at `chain/<project-id>/` under ADR-057 ACLs.
- **D7 Keys.** A **certification chain**: machine key certifies user key; user key certifies project key; project or user certifies actor and leaf keys. No derivation, so projects can move between machines.
- **D8 Governance overlays** are **tighten-only**: a project (and a nested instance) may add denies and lower limits, never relax the parent's rules. Every chain event records the effective-rule hash.
  - *D8 limits (Phase 2):* the kernel gate, the `agent.chat` tool gate and the spawned-agent gate follow live parent updates and `governance.reload`; the placement `WorkloadGate` is built from the effective rules when the control plane is built, so a push does not reach it until the kernel restarts. `max_processes` and `spawn_budget` (the concurrent sub-agent spawn cap) apply at boot; a push that changes them reports `restart_required`. The child trusts the user key in `<run>/<id>/user.pub` (written by the supervisor, outside the project tree) and falls back to its own certificate with a warning only while that pin is absent; this assumes nothing inside the project can write the run dir, which Phase 4 sandboxes must keep true.
- **D9 `project` is an ADR-099 workload kind** with pluggable sandbox drivers: `logical` (no sandbox, Phase 2), OpenShell or containers on Linux, Seatbelt or Apple `container` on macOS, wasmtime for WASM projects. The sandbox is the workload; the project kernel runs inside it as its supervisor; the user daemon supervises from outside (§6). *(Owner did not answer D9 explicitly; recorded as the analysis recommendation, reversible until Phase 4.)*
- **D10 Nested WeftOS** is isolated by default. A toggle, `weave.master = true`, marks an instance as the master of the WeftOS instances nested under it; the master manages their config (ports, registration level, governance cap). An inner instance never joins the outer mesh unless its master registers it.
- **D11 Node-id hash: SHA-256**, `node_id = hex(SHA-256(pubkey)[..16])`, as the code (`cluster.rs:323`) and ADR-099 already use. ADR-025 (SHAKE-256) and the ESP32 journal (BLAKE3) are corrected to match. *(Owner was unsure; SHA-256 chosen because it changes the fewest live ids.)* **Implemented in Phase 0**: one `node_id_from_pubkey` (`crates/clawft-kernel/src/node_id.rs`) used by mesh, cluster, registry and substrate; the substrate ACL still parses stored legacy `n-` ids.
- **D12 Commands outside any project** are decided by **governance**. The shipped default rule allows read-only commands (`status`, `doctor`, `health`, `version`, `project list`) against the user daemon and denies state-changing commands with "not in a project; run `weft project init` or pass `--project`". Operators may change the rule.
- **D13 Project kernels are processes by default.** In-process tenancy is the opt-in for small projects and the collapse for single-tenant hosts.
- **D14 Resolution.** `weft` finds a kernel by flag → env → manifest → user default, then confirms with a `kernel.status` handshake returning `{node_id, user_id, project_id, depth, parent}`. It never maps CWD straight to a socket, never falls back silently to an in-process kernel, and prints what it tried.

### Instances, federation and environments

An entity or organization stands up a **primary instance**: the WeftOS instance that holds its governance root (genesis) and decides where work goes. A primary may have **subordinate instances**, which are separate WeftOS instances (their own genesis and chain) that the primary delegates work to. Primaries and subordinates talk through the existing inter-instance surface: mesh admission with capability claims, `coordination.link` (ADR-022), chain subscription and anchoring (D6), and ADR-099 placement for delegated workloads.

For software projects the owner's model has three instances with different shapes:

| Instance | Shape | Why |
|---|---|---|
| **Development** | distributed: many developers' user daemons and project kernels on one shared mesh | collaboration; placement fans work out |
| **Staging** | a gate: a small, deliberately undistributed instance that receives a candidate, runs checks, holds the promote/reject decision and the intelligence around it | promotion must be governed, reproducible and auditable, not spread across whoever is online |
| **Production** | the deployed target, fed only by staging promotions | stability |

Promotion is a governed, chain-recorded hand-off between instances, not a mode of one instance. The same shape fits sensor fusion: leaves and edge nodes form a distributed instance; a fusion instance consumes their chains; downstream consumers subscribe.

### Core versus cog

Staging-as-a-gate, CI/CD, sensor fusion and similar purpose-specific behavior are **cogs** built on the OS primitives (ADR-100), not kernel features. The kernel keeps what every instance needs: identity and certification, chains, governance, placement, IPC and mesh, supervision, the token authority. A separate audit (card cog-boundary-01) lists everything in the WeftOS tree today that should have been a cog on those primitives. That audit is **advisory**: nothing is removed because it is listed; each item gets a keep, move later, or move now verdict with its cost, and core pieces that are correctly core are fixed in place rather than extracted.

## Amendments

- **A1 (Phase 0, legacy chain).** A kernel with no chain of its own keeps using the legacy `~/.clawft` chain and key rather than forking history. `chain.lock` guards every chain in use. While no `chain.lock` exists beside a legacy chain, the first adoption needs `weaver kernel start --adopt-legacy-chain` (also when the kernel is rooted at `~/.clawft` itself); a write within 120 s is refused as a probable lock-unaware writer. `--new-chain` starts fresh, and is refused where it would overwrite the legacy chain. Phase 1 `weaver migrate user-chain` reuses this flag family and lives beside `choose_default_chain`.
- **A2 (mic source policy).** The voice pipeline's input node is: an operator pin (`WHISPER_INPUT_NODE_ID` or `voice.mic_node_id`), else the single registered node publishing `sensor/mic`; two or more candidates, including one appearing after an automatic choice, stop speech-to-text until a pin is set. `node.register` carries no capability declaration yet; requiring a declared mic capability is on the leaf track.
- **A3 (voice principal).** Voice commands dispatch through the authorization chokepoint as an internal principal with `read, chat, write`, never `admin`. Whether cron mutations stay reachable by voice is decided in Phase 1 package G.
- **A4 (D14 scope).** Phase 0 delivered the "prints what it tried, no silent fallback" half of D14. Manifest resolution and the `kernel.status` handshake are Phase 1 packages A and D.
- **A5 (gateway bind).** The gateway's `0.0.0.0` default is changed to loopback with ADR-102 card 03; LAN exposure is an explicit choice.

- **A6 (decisions of 2026-10-01, owner accepted the recommendations).**
  - *D12 default:* `read_only` applies only to the `--profile user` daemon; every other root keeps `allow_all` until migrated; an explicit `kernel.governance.outside_project` always wins. Voice is inside the scope but is denied cron mutations. Denial `error_kind` is `project_required`.
  - *Phase 2:* one project key (node = chain = anchor key); invalid overlay at boot refuses to start; `idle_stop_secs` 1800 and never while agents, workloads or streams are active; children survive a user-daemon restart by adoption (`kernel stop` cascades unless `--keep-children`); mesh delivery to children is register-only until Phase 3; project chains start fresh with a parent-head link; existing projects opt in via `weaver project migrate-kernel`, default flips in Phase 3.
  - *Phase 3:* uid binding is TOFU on single-human-user machines and admin-approved otherwise; admission runs in observe mode for one release, then enforce after the Pi and ESP32 are redeployed; a designated `cluster_owner_uid` answers cluster verdicts, fail-closed, with a 10-minute grace for already-admitted peers; the owner's Mac adopts its existing `node.key` as the box key (new machines generate one); `user.key` keeps the migrated `chain.key` seed; the service runs as `weaver mesh serve` from a root-owned path; the local socket is 0666 with peer-credential authorization; service accounts `_weftos` (macOS) and `weftos` (Linux); user certificates last 24 h and renew at 12 h; Windows is design-only in Phase 3. On macOS a non-root LaunchDaemon writes `/var/run/weftos` only when its user is in the directory's group, so the installer creates the directory group-owned by the service group and adds the service account to it.

- **A7 (Phase 2 contracts, package A).** The shared formats every Phase 2 package codes against; the file-level plan is `docs/plans/weave-topology-p2-plan.md` section 1.
  - *One project key.* `<root>/.weftos/project.key` is the node key, the chain signing key, the anchor key and the proof-of-possession key, so a child's `node_id` equals its `project_key_id` (first 16 bytes of SHA-256 of the public key, 32 hex). Because one key signs several message types, every signature carries a domain tag: `weftos-project-cert-v1`, `weftos-project-anchor-v1`, `weftos-mesh-local-pop-v2`.
  - *Certificate.* The user key signs `"weftos-project-cert-v1\n"` plus canonical JSON (sorted keys, no whitespace, no `sig`) of `{v, type, project_id, project_pubkey, project_key_id, user_key_id, user_pubkey, serial, issued_at, expires_at}`. No root path is inside, because projects move. `expires_at` is null in Phase 2; the verifier honours it. The first key seen for a project id is certified (TOFU against the manifest); a different key for the same id needs an explicit `project.rekey`.
  - *Anchor statement.* The project key signs `"weftos-project-anchor-v1\n"` plus canonical JSON of `{project_id, project_key_id, cert_serial, seq, chain_id, head_hash, head_seq, rule_hash, at, prev_anchor}`; `prev_anchor` is the SHA-256 of the previous accepted statement including its `sig`. The user daemon attests "this key claimed head X at time T"; it cannot verify X without subscribing to the project chain, and says so.
  - *Child root.* `RootSource::Child { id, project_root }`: ephemeral files under `~/.weftos/run/<id>/` (socket, pid, lock, log, `spawn.json`, `parent-policy.json`, `state.json`), durable files under `<root>/.weftos/` (`project.key`, `project.cert.json`, `chain/`, `state/`, committed `overlay.toml`). The project walk-up never selects a child.
  - *Overlay.* Tighten-only: `deny` and `require_approval` union, numeric limits `min(parent, overlay)`, booleans `parent OR overlay`; `permit`, `deactivate`, a parent rule id (compared trimmed and case-insensitively) or a looser limit is a hard error naming the key, and an invalid overlay refuses boot. The effective-rules hash is `SHA-256("weftos-effective-rules-v1\n" + canonical JSON of {parent_hash, overlay_hash, merged rules sorted by id, merged limits})` and rides on every child chain event as `rule_hash`.
  - *mesh-local/1 (Phase 2 child registry).* `mesh.challenge`, `mesh.register` (project key proof over `weftos-mesh-local-pop-v2\n<op>\n<user_key_id>\n<nonce>\n<project_id>` (op `register` or `rekey`, nonce 32 lowercase hex issued by the user daemon, id a canonical ULID, all validated) plus the spawn nonce), `mesh.heartbeat`, `mesh.unregister`; a session expires after three missed heartbeats and a second live session for one project is refused. Until Phase 3 peer credentials, the guard is the 0600 socket, the spawn nonce and the proof of possession. Delivery to a child is register-only in Phase 2.
  - *Verified project.* `GatePrincipal` gains `project_id` and `instance_id` (absent on old payloads). `project_id` is stamped only from a `ProjectAttestation` that the daemon's `VerifiedProject` produces (cross-crate sealing is not possible, so this is by construction path plus a grep test): the kernel's own bound project, a validated token scoped to a project, or a user-signed forward header. A bare `Request.project` stays a claim. This is an isolation guard between one user's projects, not a boundary against a hostile same-uid process.
  - *Verified project, as built (package I).* The forward header is `{project_id, issued_at_ms, sig}`, signed by the user key over `"weftos-project-forward-v2\n<project_id>\n<issued_at_ms>\n<method>\n<sha256 of canonical params>\n<target child key id>"`, so it authorises one request to one child; the child accepts it once and within 5 s, and the TCP relay strips it from remote lines. Refusal kinds: `forward_unavailable`, `forward_bad_signature`, `forward_expired`, `forward_replayed`, `project_scope_mismatch`, and the reserved `forward_wrong_target` (a header signed for a sibling child currently reports as `forward_bad_signature`). A method containing a newline is refused on both sides; the proxy stamps the header as its last step, after any param rewriting. A token scoped to one project cannot act as another (`project_scope_mismatch`). Honest limit: same-uid callers can still lie via `Request.project` on the claim path (no token, no forward header, unbound daemon), which keeps its Phase 1 meaning and is logged as `claimed`; `VerifiedProject` is an isolation guard between one user's projects, not a boundary against a hostile local process (Phase 3 peer credentials, Phase 4 sandboxes).
  - *Child bootstrap, as built (package H).* `pre_boot` reads and deletes `spawn.json` (0600, 60 s, wall clock), loads `project.key`, registers over `mesh-local/1`, verifies and persists the certificate and verifies the signed parent policy before the chain is opened. The register acknowledgement is signed by the user key over child-chosen randomness, so a socket squatting at the parent path cannot forge one; registration is also bound by a second project-key signature over socket, pid and client nonce, and heartbeat and unregister carry a project-key signature over (op, session, pid, time), so a leaked session id is not a credential. The pid in `project.register` is recorded as `claimed_pid`: the child reports it and the user daemon does not verify it (it checks it against the pid the supervisor spawned, which the supervisor records on the spawn expectation right after starting the process; a registration that wins the race before that is not checked). Removal of `spawn.json` is by path after the descriptor checks. The anchor acknowledgement is not signed (transport-authenticated, as in A7 above). *Revocation reach:* `project.rekey` drops the session (the old key's re-register is refused `key_revoked`) and writes no marker, so the rekeyed child boots under its new certificate. `project.revoke` is terminal: it drops the session and writes `~/.weftos/run/<id>/revoked` (atomic, 0600; the run dir is created 0700 when the child is stopped), and nothing clears it, and since the Phase 2 review a revoked id never re-enrols at all (`project_revoked`, see *Phase 2 review* below). A running child whose re-register is refused `key_revoked`, `key_conflict`, `key_reuse`, `project_not_found` or `project_revoked` shuts the kernel down; a child booted while the parent is unreachable refuses only if the marker exists, so it cannot see a revocation issued while the user daemon could not write it. A challenge nonce that was evicted or used is refused `challenge_unknown` and the child asks again, for at most 45 s of retries (under the 60 s spawn window). A heartbeat proof covers the reported activity and is replayable for at most 30 s (liveness only). `--profile project` forces the project profile in `daemon::run`, so a project kernel cannot boot as a plain kernel.
  - *Supervisor, as built (package G).* The user daemon runs one `Supervisor` (`weave/src/project_supervisor/`). A child is the `project` workload kind on the `logical` adapter (`clawft-kernel`: `ProjectKind`, `LogicalRuntime`, a `ChildLauncher` trait weave implements), driven through `WorkloadHost`, so every transition is gated and chained as `workload.*`. The only permit for the kind is `project_supervisor_permit()`, limited to the principal `weftos.project-supervisor` and `PackageTrust::ProjectCert` (which ranks below every signed-package trust, so no cog permit ever matches it); it is not installed in the operator placement gate, and `ProjectKind::load` always refuses, so `workload.place` of a project stays denied. Deviations from the plan, and why: (1) children are **not** launched with `workload_runtime::supervise::Supervised`: it pipes stdout and stderr, so a child that outlives a daemon restart would die of `SIGPIPE`; children log to `<run>/<id>/kernel.log` in their own process group; (2) restarts use a **local `RestartTracker`** (OTP `one_for_one` plus `Transient`, backoff 1 s to 30 s, `restart_max` inside `restart_window_secs` then `failed`) because the kernel `os-patterns` tracker backs off from 100 ms; (3) a run root whose `<run>/<id>/kernel.sock` exceeds 103 bytes is **refused** (`sun_path`), found by a test on macOS; (4) the user-daemon stop cascade is **CLI-side** (`project.stop_all` before SIGTERM; `--keep-children` skips it), so `daemon.rs` shutdown is untouched, and launchd `AbandonProcessGroup` / systemd `KillMode=process` keep children across a service restart or `weaver update`; (5) the child environment is an allow-list after `env_clear()` (`HOME`, `PATH`, locale, `WEFTOS_RUNTIME_DIR`, `WEFTOS_PROJECT_ID`), argv is exactly `kernel start --foreground --profile project --project <id>`.
  - *Project token (package G).* `TokenScope::Project`: `write` capability only, never Admin, bound to one project, TTL 3600 s, renewed through `project.token.refresh` (route `Write`) by the child's `ParentLink` when 900 s remain (before each call and from its monitor, at most one attempt per 30 s). The supervisor honours a refresh only for the token it issued last or the one before and revokes the older; stopping or failing a project revokes both. In addition `authorize_caller` refuses every method outside `project_token_scope::ALLOWED_METHODS` / `ALLOWED_PREFIXES` (`shared.`, `kernel.handshake`, `project.token.refresh`) with `project_token_method_denied`: what the `ParentLink` calls and nothing else. The child's other parent calls (`mesh.*`, `project.anchor.submit`) do not present the token. Honest limit: a same-uid caller sending the literal scope `admin` (ADR-070) bypasses this like every capability check until Phase 3 peer credentials. Known limitation: tokens live in the chain, which is saved only on a clean shutdown, so after an unclean user-daemon exit a surviving child's token is unknown, its refresh fails closed, and its shared services stay `down` until the child is restarted (`weaver kernel restart --project <id>`). Adoption cannot re-issue a token to a running child because there is no channel to deliver it.
  - *Adoption, revocation, markers (package G).* On boot the supervisor scans `<run>/*/kernel.pid` and adopts only a child whose pid is alive, whose executable name matches the one recorded in `state.json`, whose `kernel.lock` is held by that pid and whose `kernel.handshake` names the project and the same pid; an unverifiable leftover is listed (`weaver kernel status`, `weaver doctor`) and never signalled; a pid is re-verified before every signal (SIGTERM and SIGKILL), and an adopted pid is group-signalled only when it leads its group. A verified child of a project that no longer prepares is never left unmanaged: a revoked project's child is stopped, anything else is reported with the reason. `ensure_running` takes over a live verified child instead of starting a second. After a SIGHUP re-exec the daemon is still the parent of its children but has no waiter, so adopted pids are reaped with `waitpid(WNOHANG)` to tell a dead child from a zombie. G is the single writer of the terminal `<run>/<id>/revoked` marker: `project.revoke`'s identity hook (`on_identity_change`, after the journal write) writes it (0600, run dir 0700), and nothing ever clears it; the supervisor kills the child's credentials first, stops it (falling through to signals if the gated stop is refused), marks the project `failed` and never respawns it; `project.rekey` and a repair that changes a bound key stop the old child and write no marker.
  - *Legacy daemons (package G).* A plain `weaver kernel start` inside a project, beside a running user daemon, is refused unless `--legacy-project-daemon` (one release); a re-exec (`SIGHUP`, `weaver update`) and the backgrounding of an already-allowed start carry the flag so the refusal never takes a running daemon down. The guard is skipped when `WEFTOS_RUNTIME_DIR` names the endpoint explicitly. `weaver project migrate-kernel <id> [--dry-run|--revert]` is the per-project opt-in: it refuses while the project's own daemon runs (never signalled), refuses symlinked sources or directories (re-checked at apply time, copies written `O_NOFOLLOW`), copies `workloads.json` and `apps.json` to `<root>/.weftos/state/`, flips `[serve] via` and prints the rollback line.
  - *Parent transports (package G, H).* One transport for `project.anchor.submit`: H's `RpcParentTransport` (it verifies the parent socket's owner and mode and bounds the whole exchange). G's own was removed. `ParentLink` (shared services and token refresh) keeps its own bounded client because it is async and carries the project token.
  - *Integration (Phase 2).* The user daemon's `post_boot` installs the supervisor, runs the adoption scan and starts the idle loop. The only permit for the `project` kind stays `project_supervisor_permit()` on the supervisor's own workload gate; it is not in the operator gate, so `workload.place` of a project is still denied. One derivation names the revoked marker, `runtime_paths::revoked_marker(run_root, id)` (`<run_root>/<id>/revoked`): the `project.revoke` writer and the supervisor use the user daemon's run root (`project_cert_rpc::user_run_root`, which `post_boot` and `governance.parent.push` also use, so `$WEFTOS_RUNTIME_DIR` is honoured; with no run root the push is refused `no_run_root`), and the child reaches the same file as `RuntimePaths::revoked_marker()` of its run dir. Before this, the writer derived it from the manifest store (`<manifests>/../run/<id>/revoked`), which a `$WEFTOS_RUNTIME_DIR` or a moved store pointed elsewhere. The end-to-end test with a real child found two more wiring gaps, both fixed: a child's chain was signed by a fresh `chain.key` beside the checkpoint instead of `project.key`, and `post_boot`'s one-key check then stopped every real child (boot now signs a `project`-profile chain with the project key `pre_boot` handed over as the node key seed, confirmed against `project.key` by the strict reader; a missing seed, a missing file or a different key refuses the boot, and nothing is created), and a child was bound to no project (`compute_bound` now binds `RootSource::Child` to its id), so its handshake failed the supervisor's readiness check, a forward header (the graceful `kernel.shutdown`) could not verify, and governance events carried no `project_id`.
  - *Revoke marker fails closed.* When the marker cannot be written (no user-daemon run root, an id that is not a safe path component, or an I/O error, each with its own message), `project.revoke` still completes the revocation (journal, chain, session, child stop) and then returns `revoke_marker_unwritten` instead of success, so the owner can write the marker by hand; an identity repair that revokes reports it the same way.

Declined: a `daemon::run` smoke test for the project profile with decoys beyond what `shared_services_child.rs` and the end-to-end test's real child already prove (the heavy half needs the real `weaver` binary and is the e2e's job); the `.env`-in-project-root case (S10e) stays open. - **A10 (Phase 3 review, 2026-10-02; `docs/research/daemon-topology/phase-3-review.md`).** What the review established about the shipped behaviour; no decision is reopened.
  - *Verdict caching compounds:* the kernel's admission gate and the service's verdict broker each cache a permit for up to 300 s, so a governance rule change can take up to about 600 s to reach a peer that is already permitted. Denials cache for 30 s.
  - *`observe` is not protection:* under `observe` (the default for the first release) no peer is ever marked verified, so a peer can still take over another's route by claiming its `source_node`; route ownership and `src_scope` are enforced only under `enforce`. `weaver mesh peer revoke` closes the peer's live connection in every mode, and under `enforce` a revoked peer is also cut off on its next frame and refused on reconnect; under `observe` it can reconnect.
  - *User chain in service mode:* the migration (plan section 5) modifies nothing under `~/.weftos/chain/`, but in steady state the service-mode user daemon appends `mesh.service.bound` and `mesh.journal.anchor` events to its user chain. "Never touched" applies to the migration only.
  - *Identity is never changed by omission:* `weaver mesh install-service` refuses on a machine with `~/.weftos/run/node.key` unless `--adopt-node-key` or `--fresh-node-key` is given, and under `auto` a user daemon whose machine key is pinned and that has no local `node.key` refuses to boot rather than mint a new node id.
  - *Observe takeover is a flap, by design:* under `observe` an unverified connection that claims a `source_node` already routed to another unverified connection replaces that route, and the displaced connection is closed within 250 ms (its route is gone). The legitimate peer then reconnects and takes the route back, so a persistent claimant produces a flap rather than a silent hijack. We do not refuse the displacement: a legitimate reconnect after a wifi blip looks identical (the old connection may be half-open for minutes) and must win. The replacement is logged at warn. Only `enforce` makes a route non-displaceable.
  - *Connection limits apply in every mode:* the per-IP cap and the first-frame timeout apply under `off`, `observe` and `enforce`; only the idle timeout and live revocation checks remain `enforce`-only. A legacy leaf must therefore send something within 10 s of connecting. Both are configurable, with the same defaults, in each place the mesh runs: `kernel.mesh.max_connections_per_ip` (64) and `kernel.mesh.first_frame_timeout_secs` (10) for the collapsed daemon, and `max_connections_per_ip` / `first_frame_timeout_secs` in `mesh.toml` for the machine mesh service (`weaver mesh install-service` writes them only when `--max-connections-per-ip` / `--first-frame-timeout-secs` are given). The service passes them to the listener through `serve_listener_with`.
  - *Route loss is O(1) per connection:* each serving connection counts its own live routes (`RouteTally`), flipped by removal or replacement, instead of scanning the peer map every 250 ms.
  - *Seed dials are bidirectional and redial:* `connect_seeds` runs the same pump as the listener, so frames from the seed reach the runtime, and redials with jittered exponential backoff (1 s doubling to 60 s, 50-100% jitter, reset after 30 s up). The seed route is keyed by the dialled address until the seed's own envelopes register its node id on the same connection. The returned handles stop dialling when aborted, and `MeshService::stop` (and drop) aborts them together with the accept loop; stop is terminal for those loops. A dialled connection that hears nothing for 5 minutes is dropped and redialled (inbound silence only, so a half-open seed is detected). The seed's id is not authenticated (no hello comes back), so the connection binds to the first `source_node` it sends, drops later frames claiming another id, and may not claim an id another connection already routes. Duplicate seed addresses are dialled once. A route removed by aborting a dial emits `Left`.
  - *Relays that predate scope fields strip them:* the wire format ignores unknown fields, so a peer on an older build accepts newer envelopes, but if it relays one it re-serialises without `dest_scope` and `src_scope`. Scoped traffic must not cross such a hop; treat a missing scope as unscoped, never as trusted.
  - *Quiet seeds flap every 5 minutes:* the dial side has no keepalive, so a seed that sends nothing for 300 s is treated as half-open, dropped and redialled; its route emits `Left` then `Joined` each cycle. Seeds that publish or heartbeat more often than that are unaffected. A dial-side keepalive is a follow-up.
  - *Unverified peers still reach cluster membership:* under `off` and `observe`, a peer that sends an envelope is registered under its claimed `source_node` and joins cluster membership as `Active` through the first-envelope path, as before. Only the early join at admission is limited to admitted peers. Carrying a `verified` flag on `MeshPeerEvent::Joined`, so membership can tell the two apart, is a follow-up.
  - *Responders join on authentication, not first frame:* a connection whose hello verified registers its route under the verified node id (and emits the cluster `Joined`) as soon as admission completes, for admitted peers only; a key-valid peer under `off` or `observe` is not a member and keeps the first-envelope path. If the route is refused the connection is closed. The cluster node id is the Ed25519-derived node id (key on the Ed25519 node key; the Noise static key is bound to it by the hello), stable across restarts because it is derived from the persisted key rather than generated per boot.
  - *Torn tail vs corrupt tail:* a lone torn final line (no newline, nothing readable in it, no earlier pending quarantine) is the signature of a crash during an append and was never acknowledged to a caller, so the service accepts it at start and journals `journal.accept_truncate` with `auto: "torn_tail"`; this keeps a power loss from killing every user link at the 12 h renewal. It was chosen over letting renewals run while read-only because a lost `rebind` in a quarantined tail is not visible in the harvested facts, so renewing the old key could resurrect a replaced key. Any other bad tail (complete line with a bad signature or hash, over-long line, several lines) still quarantines and needs an admin acceptance.
  - *Record publication:* the service stages `service.json` under a temp name, binds the socket, and renames the record into place only after the bind succeeds, so a service that loses a bind race never replaces the winner's record (this replaces the record-before-socket order in A9; clients already wait up to 2 s for a record that is a moment late).

A7's "mesh-local/1 (Phase 2 child registry)" bullet and A9 both use the bare name for different protocols; read them with this table.

Keep `mesh-local` for the service link, where the name describes the machine-local mesh path. - **A13 (user-key rotation, 2026-10-02; review follow-up e19c3af1).** The user key (`~/.weftos/user.key`) can be replaced without orphaning what the old key sealed.
  - *Rotation record.* `weaver migrate user-key --rotate` (offline: it probes the user chain's `chain.lock` and refuses while the user daemon runs, because the daemon holds the old key in memory) writes a **dual-signed handover**: `{v, seq, old_pubkey, old_key_id, new_pubkey, new_key_id, rotated_at, prev}` signed by BOTH keys under `weftos-user-key-rotation-v1`, hash-linked (`prev` is the SHA-256 of the previous record including its signatures) into the append-only `<manifests>/user-key-rotations.jsonl` (0600). The daemon chains each record as a `user.key.rotated` event (source `user.projects`) the next time it builds its certificate environment (idempotent; a record that cannot be chained is a warning, the log stays authoritative). The steps are resumable: the new seed is staged as `user.key.next`, the record appended, the old `user.key` moved to `user.key.retired-<seq>` (kept, 0600; code never deletes a key), then `user.key.next` becomes `user.key`. Running the verb again after a crash completes the same record. A user key that exists only as the migrated `chain.key` is rotated by writing a new `user.key` (the chain loader prefers it); `chain.key` is not touched.
  - *What verifies across a rotation.* `UserKeyHistory` folds the log into "current key plus retired keys with their rotation point"; the history must end at the key the daemon actually holds (`NotCurrent` otherwise, and every identity call fails closed with `user_key_history_invalid`, as for a corrupt identity journal). A retired key is accepted for material dated at or before its rotation point and refused after it. **Chain-anchored rule for certificates:** a certificate sealed by a retired key counts only if, besides being dated at or before the rotation point, a `project.register` or `project.rekey` event on the user chain carries it with a sequence below that key's `user.key.rotated` event. A journal line or `<id>.cert.json` alone is never evidence, because only the daemon appends to the reserved chain source and whoever holds the old private key can backdate a claim (a backdated old-key certificate with a high serial is dropped). Anchor records (`<id>.anchor.json` `rec_sig`) are judged by the sealed statement's `at` only. A certificate in force that an older user key sealed keeps verifying for `project.anchor.submit`, so a running child continues anchoring; a child **started after** the rotation is pinned to the new key and registers normally. A child that was already running (or adopted) signs its proof of possession with the user key it was pinned to, so its `mesh.register` after the rotation fails `pop_failed`; that is neither fatal nor a spawn-nonce kind, so it keeps running unregistered until the supervisor's liveness pass (three missed beats plus the 30 s `lost_heartbeat_grace`) restarts it, and the restart pins the new key. The child heals by a forced restart, not by re-certification; `weaver kernel restart --project <id>` does the same at once.
  - *Parent policies and children.* Policies, forward headers and the `user.pub` pin are signed or pinned under the key in use at spawn. The supervisor re-signs and re-pins on every spawn, so a child started after the rotation is consistent; a child that was already running keeps the old pin and rejects policy pushed under the new key until it is restarted (`weaver kernel restart --project <id>`). Children do not read the rotation log. Phase 3's user certificate (24 h) and machine binding follow the key through `weaver mesh bind rebind`, and the old certificate expires on its own. A daemon crash that loses the unsaved chain also loses the chain evidence of old-key certificates; those projects then re-register (fail closed).
  - *Rotation log durability.* If `user-key-rotations.jsonl` is deleted or shorter than the chain's verified `user.key.rotated` records, the daemon rebuilds it from the chain when it builds its certificate environment, or refuses with an error naming the cause if those records do not end at the key in use; a missing log never silently downgrades verification. *Crash window.* `weaver migrate user-key --rotate` holds the chain lock through the swap, completes a half-done rotation on re-run (including the state where `user.key` is missing and `user.key.next` is present), never overwrites an existing `user.key.retired-<seq>`, and warns when `chain.key` still holds the retired key.
  - *Known limits.* Anchor records are dated by the statement's `at`, so whoever still holds the OLD private key can backdate those past the point. After a suspected compromise, rotate and also `project.rekey` or `project.revoke` the affected projects (the user chain, signed by the new key from the first post-rotation boot, is the tamper-evident record of what was accepted when). The on-disk chain checkpoint keeps the signature it was saved with; nothing re-signs history.
- **A14 (identity-trust follow-ups, 2026-10-02; reviews P1 S3, P2 S2 and S9).**
  - *Anchor reset (P2 S2).* After a project chain is moved aside the project restarts its anchors at `seq = 1`; the user daemon, holding the old head, refused every retry (`anchor_seq`). The owner runs `weaver project anchor reset --project <id> [--reason ...]` (RPC `project.anchor.reset`, Admin, user daemon only, a token is refused). It appends a `project.anchor.reset` event to the user chain and writes `<manifests>/<id>.anchor-reset.json`, a sealed copy (user key, `weftos-project-anchor-reset-v1`). The chain event is the authority: an epoch counts only when it is exactly the previous epoch plus one, and a record file without a matching chain event changes nothing (a daemon crash that loses the unsaved chain loses the reset; the owner repeats it). It opens a new **epoch**: statements and records of an earlier epoch remain as history and are never the baseline, so the next accepted statement is `seq = 1` with no `prev_anchor`. `Accepted.epoch` is part of the sealed record only when non-zero, so old records keep verifying. The daemon cannot tell a deliberate chain reset from a project that merely lost anchor state: the owner decides, a project that did not reset keeps submitting N + 1 and is refused until it restarts its anchors, and a reset with nothing accepted in the current epoch is refused `anchor_nothing_to_reset`. Within an epoch a statement's `chain_id` must equal the last accepted one (`anchor_chain_id`).
  - *Child peers (P2 S9).* ADR-070's same-uid shortcut honoured a literal `auth: "admin"` from any peer with the daemon's uid, which includes a compromised supervised child, which could then mint an owner token. The user daemon now classifies each unix-socket peer at accept (`child_peer`): a same-uid peer whose process group is a supervised child's (children lead their own group, `process_group(0)`, so the group id is the child's pid; the supervisor exposes `Launcher::supervised_pids`) is `Child`. A same-uid peer whose pid is unknown or whose process group cannot be read (it exited and was reaped before accept) is also a `Child`: the classifier fails closed. The supervised set is every child process group this daemon started or adopted, kept until `killpg(pgid, 0)` reports `ESRCH` (so grandchildren orphaned by the leader's exit are still recognised; the check never reaps). The Windows named-pipe path and the legacy `handle_connection` wrapper do not classify and default to Owner. A `Child`'s literal scopes are ignored and it is treated as anonymous (read and chat), not refused, because a child's own parent calls (`kernel.handshake`, `mesh.*`, `project.anchor.submit`) carry the client library's implicit `"admin"` and need only `read`; only its project token is honoured, and that token is write-only and method-restricted (`project_token_method_denied`). The owner's CLI is in no child's group and is unchanged. *Not done, and why:* stripping `wft_` tokens in the TCP relay. No code path carries a token into a child (the user daemon calls a child only with a signed forward header), remote callers legitimately authenticate with `wft_` tokens (ADR-102 D3), and with the mint hop closed a child cannot obtain an owner token to relay. *Honest limit:* this is a narrowing, not a boundary. A child process that leaves its group (`setsid`, `setpgid`, a double fork) escapes it; the boundary is a separate uid or a Phase 4 sandbox.
  - *Token project scope (P1 S3).* Enforced, as amended in A8: the token's project is the request's project and a differing claim is `project_scope_mismatch`. Not a capability limit: an owner token labelled with a project still holds owner scope over user-level methods.
- **A15 (service-stamped delivery origin, 2026-10-03; ADR-106 section 5.3, phase 1c).** The daemon could not tell who a `deliver` came from: the frame carried a claimed `source_node` and an optional certificate, and `MeshSink` built `PeerCtx::unauthenticated`. The service now vouches for the origin.
  - *Protocol.* mesh-local `PROTO_MAX` is 2 (`PROTO_MIN` stays 1). A new constant `PROTO_ORIGIN = 2` names the first version whose `deliver` carries `origin`: `{"kind": "admitted_peer", "node_id", "class": "node" | "leaf" | "other"}`, `{"kind": "local_tenant"}` or `{"kind": "unadmitted"}`. The field is optional; an unknown kind or class decodes to `unadmitted` or `other`.
  - *Service side.* `TenantRouter` stamps it, and only from what it knows about the connection: an inbound delivery is `admitted_peer` exactly when the kernel listener set `PeerCtx::node_verified` (admission verified the id), with the id admission verified and its class; anything else is `unadmitted`. `deliver_local` (one tenant to another on the machine) stamps `local_tenant`. The stamp is written only to a registration whose connection negotiated version 2 or higher (`Registration::proto`). The service never forwards an origin from a tenant: a `deliver` frame sent by a tenant is `unsupported`, and a tenant's `send` carries a `KernelMessage` whose contents are never read as an origin.
  - *Daemon side.* `Deliver::effective_origin(negotiated)` returns `unadmitted` below `PROTO_ORIGIN` and when the field is absent, so a daemon talking to an older service reads every delivery as unadmitted. `MeshSink` records the version of each (re)connected link and builds the peer context from the stamped origin: `admitted_peer` with class `node` becomes a verified node (`node_verified`, `PeerClass::Node`, `peer_id` the vouched id), class `leaf` a verified leaf, and `local_tenant`, `unadmitted`, an unknown class and a missing stamp stay unauthenticated. The stamp is believed only on a link whose `MeshLocalClient` connected, which means the service peer-credential check (root or the `service.json` uid) and the hello key proof passed; a failed check never yields a link. The daemon must not be built with `clawft-mesh-local`'s `testing` feature, which injects a fake server credential: `scripts/build.sh gate` check 21 (`check-daemon-no-mesh-testing`) fails if the daemon's dependency graph enables it. On a single-user install where `service_uid` equals the daemon's uid, `admitted_peer` is only as strong as that uid, which could already act as the daemon.
  - *Who uses it.* The cog mesh (`mesh.cog.checkout`, `mesh.artifact.tunnel`, ADR-106): only a verified node is served or accepted. The A2A router still ignores the context. The A12 table's `PROTO_MAX = 1` is now 2.
  - *Tests.* `crates/clawft-mesh-service/src/router_origin_tests.rs`, `crates/clawft-weave/src/mesh_local_sink.rs` (unit), `crates/clawft-weave/tests/mesh_cog_checkout_e2e.rs` (the real service, unix socket, client, sink and router).

- **A16 (licence records through the service, 2026-10-03; ADR-106 phase 3 part A).** The service runtime consumes `mesh.cog.binding`, `mesh.cog.grant` and `mesh.cog.sync` as control topics. It now installs a sink for each (`clawft-mesh-service` `licence_forward`) that hands a record from a licensed peer (admission verified, class `node`) to the reserved-topic holder's registration, stamped as in A15, and drops and counts anything else (`licence_unlicensed`). The reserved-topic rules of ADR-106 1c are unchanged. `peers.list` replies gain `licensed`: the connected peers whose route admission verified with class `node`. The service holds no licence state and adds no signing call; the user daemon signs placement and steward requests with its own control key (ADR-106, "the service-mode signer").

## Consequences

- One resolver for every runtime file; a second daemon for the same scope refuses to start; `$HOME` is never a project; the mesh node id is stable and derived from the node key.
- ADR-102's token authority moves to the user role; tokens can carry an optional `project_id` scope; the playground gets a project selector.
- `weaver update` restarts the user daemon found via its PID file and, per project, the kernels it supervises, recording binary path and sha in the manifest.
- The existing project-local daemon on the owner's Mac (other project, PID 70730) is migrated in Phase 1 by the owner (stop, register as the first manifest entry); it is not stopped automatically.
- Three tiers (service, user daemon, project kernels) can run different versions, so every local protocol (`mesh-local/N`, daemon RPC) is versioned and negotiated from Phase 1.
- The leaf path needs provisioned keys and a parent-side admission gate; until then unsigned leaf publishes stay a bring-up exception that doctor flags.

Known limits of Phase 3 admission (K1): a peer's class (`node` or `leaf`) is self-declared in its signed hello, so a node can claim leaf limits it does not need or omit them; under `enforce` the verdict source may override the class, and binding class to an issued credential is future work. `genesis_hash` is a cluster label, not a credential; membership is the verdict source's decision, and `enforce` without a governance gate refuses everyone unless `admission_open_membership` is set. Only an *admitted* peer (hello verified, `enforce`, verdict permit) is treated as verified for route ownership and `src_scope`.

Known limits of the Phase 3 user-daemon mesh client (U): a `verdict.reply` carries `rule_hash`, which is a hash of the gate's witness (permit token or deny receipt) and is empty when the gate produced none; it is a verdict witness, not a rule identity, until the overlay runtime's rule hash (package E) is available to the gate. The service may cache a permit for up to 300 s (`ttl_s`), so a rule change reaches already-permitted peers only after that window; denials cache for 30 s. `service.json` is read once at boot; a legitimate machine key rotation needs `weaver mesh trust` and a daemon restart. A daemon that fell back to collapsed mode (`auto`, no service at boot) does not switch when a service appears; it logs loudly and needs a restart.

Known limits of the Phase 3 installation (H, X): the macOS service log `/var/log/weftos/mesh.log` is not rotated (launchd holds it open; os_log or self-rotation is follow-up work). Windows is design only (plan section 6): the service refuses to start there. On macOS the service can start before the rundir helper recreates `/var/run/weftos` at boot; launchd's throttle restarts it until the directory exists, so the two converge within seconds rather than by ordering. The installer receipt's `tiers` list is read by `weaver doctor install` but nothing writes it yet, so the service tier is taken from `service.json` alone. The service does not yet emit `unsigned_leaf_peers` in its status, so the doctor's leaf check never fires. The two-uid paths are exercised with an injected peer identity in the suite and for real only by `scripts/dev/mesh-two-uid.sh` (sudo, never in the gate).

Known limits of the Phase 3 machine service (S): under `enforce`, admission depends on the cluster-owner daemon being reachable. Asks are budgeted (10 per peer node id and 120 per minute in total, of which 60 are reserved for peers that already hold an allow entry) and a granted peer keeps its permit for `stale_grace` after the grant expires, but a sustained flood of new node ids can still delay *new* peers' admission while the owner is slow or away; existing members are not affected beyond the grace window. The cluster owner is never inferred from a TOFU bind: `enforce` needs an explicit `cluster_owner_uid`. `accept_from` governs local cross-tenant sends only; deliveries from admitted remote peers are gated by admission. A revocation made while the journal cannot be written is enforced in memory (and `revoked.json`) but is journalled only if a later append succeeds; the operator gets a warning.
