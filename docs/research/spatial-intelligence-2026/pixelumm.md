## 1. What it is

**PixelUMM** ([arXiv:2609.38597](https://arxiv.org/abs/2609.38597), submitted 2026-09-29; Wei, Ren, Chu, Ren, Ling, Huang, Leal-Taixe, Fidler, W. Chen, Z. Wang, J. Wu; NVIDIA Toronto AI Lab) is one transformer that does image and video **understanding** (text out) and **generation** (pixels out) with **no vision encoder and no VAE**. **READ**

- Images are split into 16x16 pixel patches. Video becomes 4x16x16 spatiotemporal tubelets. A single linear layer maps each patch or tubelet into the hidden space. **READ**
- Text is autoregressive. Pixels are generated by flow matching directly in pixel space. **READ**
- The point is architectural: today's unified models bolt a ViT/SigLIP encoder onto understanding and a VAE onto generation. Removing both leaves one raw-pixel interface for both directions. **READ** (abstract); the "why it matters" gloss is **INFERRED**.

It is a **dynamics-and-appearance model that renders pixels**. In the Airtree taxonomy used in S2 it sits with the video generators, not with spatial intelligence. **INFERRED**

## 2. Verdict

**Watch (C). Pattern-only on one idea. Do not adopt.**

Reason: (1) the weights are **non-commercial research only**, (2) it is **15.2B parameters / ~61 GB checkpoint, CUDA + FlashAttention only**, with nothing for Apple Silicon, (3) the paper itself says camera control, 3D geometry and explicit spatial control are **not covered**, and (4) it generates 512px, 96-frame clips, so it is not a persistent world and gives Urth nothing metric. Every claim above is **READ** except the conclusion.

The one pattern worth keeping: **token-level hard routing between an understanding expert and a generation expert over shared attention**. That is a clean template for "one backbone, two privileged paths" if we ever need a single local model that both describes a scene and renders a preview. **INFERRED**

## 3. Architecture

| Piece | Detail | Tag |
|---|---|---|
| Backbone | Decoder-only transformer on **Qwen3-8B**; Mixture-of-Transformers with separate understanding and generation experts | READ |
| Attention | **Shared** self-attention across text, clean pixel tokens and noisy pixel tokens | READ |
| Routing | **Hard, token-level**: text + clean visual tokens go to the understanding expert; noisy visual tokens go to the generation expert | READ |
| Patchify | 2D 16x16 (32x32 tested); 3D 4x16x16 tubelets; one linear projection per path | READ |
| Generation objective | Flow matching, **x-prediction** with velocity-space loss, `z_t=(1-t)x+t*eps`, clipped timestep `max(t,0.05)` | READ |
| Sampler | DPM-Solver, 50 steps, CFG 3.5-6 in qualitative examples. No latency figures given | READ |
| Sizes | **1.7B** (ablations) and **8B** (released). The 8B figure is the backbone; the model card lists the full model at **~15.2B** | READ (both numbers) |
| Video understanding modes | Dense (4 fps, tubelets) and sparse (1 fps, per-frame); reported comparable. Up to 96 sampled frames at eval | READ |

The 8B vs 15.2B gap is almost certainly two experts of roughly backbone size sharing attention. The paper text we fetched does not state the split. **INFERRED**

**Training (READ):** six progressive stages, about 505K steps in total: joint text/I2T/T2I at 256 squared; T2I + T2V at 256 squared; three video-understanding stages (native, 224, 448); joint stage 2 at 512 (images) and 448 (video). Data: FineVision (images), VideoChat-Flash and LLaVA-Video-178K (video understanding), "public generation data". The 8B needed roughly a third of the steps of the 1.7B for equal loss. GPU-hours are **not stated** in what we read.

**Known artifacts (READ):** patch artifacts in low-texture regions at high CFG with the linear pixel head (conv/PixelShuffle heads reduce it); bodies merge when many similar entities appear; hands and fine anatomy are weak; physics and interactions can be implausible.

## 4. Results

All **READ**; nothing independently reproduced.

| Area | Benchmark | PixelUMM 8B |
|---|---|---|
| Image understanding (21 tasks, lmms-eval) | MMMU / MMStar / TextVQA | 41.67 / 53.99 / 78.76 |
| | DocVQA / RealWorldQA / GQA / CountBench | 90.42 / 71.63 / 61.90 / 94.30 |
| Video understanding | MVBench / Video-MME / LongVideoBench / LVBench | 70.53 / 57.33 / 59.61 / 40.41 |
| Image generation | GenEval overall / DPG-Bench overall | 0.77 / 85.74 |
| Video generation (VBench) | Quality / Semantic / Motion smoothness | 84.10 / 79.80 / 98.70 |

Generation output: **512x512, 4.0 s, 24 fps, 96 frames**. **READ**

Read honestly: understanding numbers are "competitive for an encoder-free 8B", not frontier (MMMU 41.67 is low). VBench is a clip-quality score, not a world-consistency one. We have no WBench Navi score, so it cannot be placed on the S2 leaderboard. **INFERRED**

## 5. Comparison

| | **PixelUMM** | **image-blaster (S10)** | **Feed-forward recon (S3: VGGT, MASt3R, SpatialLM)** |
|---|---|---|---|
| Input | Text, image, video | One photo | Unposed images / video |
| Output | Text, 512px image, 96-frame video | Marble splat + collider GLB, object meshes, SFX | Cameras, depth, pointmaps, tracks; layout boxes (SpatialLM) |
| 3D / geometry | **None** (not covered, READ) | Yes, but invented | **Yes, from observation** |
| Metric? | No | No (approximate `metric_scale_factor`) | Partly: VGGT not guaranteed, MASt3R metric ckpt, up-to-scale otherwise |
| Persistence | None; one clip | Persistent files on disk | Persistent; feeds COLMAP-shaped `sparse/0` |
| Runs where | Local CUDA, ~15B | Hosted APIs (World Labs, FAL); images leave the machine | Local GPU; VGGT 1B |
| Weights licence | **NVIDIA One-Way Noncommercial** | Closed APIs; repo MIT | VGGT has a commercial ckpt; MASt3R CC BY-NC-SA; SpatialLM Sonata NC (per S3) |
| WeftOS role | Watch | Two patterns (lift-or-push, request-JSON), no code | **A: pose adapter and W1 layout proposer** |
| ADR-079 status | Cosmetic | `generative_cosmetic` | Proposal, `vector: None`, honest scale |

**Against image-blaster:** both are generative, but image-blaster ends in a persistent splat + collider + per-object meshes with physics modes, which maps onto ADR-078's leaf split. PixelUMM ends in pixels. image-blaster is the closer cousin to Urth's appearance layer; PixelUMM is the closer cousin to the S2 video models. **INFERRED**

**Against feed-forward reconstruction:** these are opposite directions of the same photo-to-world problem. S3 turns pixels into cameras and structure (observation, proposal, metric or honestly unscaled). PixelUMM turns text and pixels into more pixels. PixelUMM cannot replace any S3 stage and S3 cannot caption or render. **INFERRED**

## 6. Local-inference feasibility

| Item | Finding | Tag |
|---|---|---|
| Weights | Public: Hugging Face `nvidia/PixelUMM`; two checkpoints, `S8-F22-R05` (default, all four tasks) and `S8-F18-R01` (generation + image understanding only) | READ |
| Code | github.com/nv-tlabs/PixelUMM, **Apache-2.0**, with one DiT-derived file (`modeling_utils.py`) under CC BY-NC 4.0 | READ |
| **Weights licence** | **NVIDIA One-Way Noncommercial License**: non-commercial research or evaluation only. Commercial use **not permitted** | READ |
| Parameters | ~15.2B (model card) | READ |
| Checkpoint size | ~61 GB listed for the output checkpoint | READ |
| Precision | Not stated. 15.2B x 4 bytes is ~61 GB, so the listed file looks like **fp32**; bf16 would be ~30 GB | INFERRED |
| Stated hardware | Linux, NVIDIA GPU, CUDA PyTorch, FlashAttention. Toy training example: seven GPUs with 48 GiB each | READ |
| Inference VRAM | **Not stated.** bf16 weights alone ~30 GB, plus activations for 96-frame tubelet sequences and CFG (two passes) | INFERRED |
| Apple / MPS / quantization | **Not mentioned** anywhere | READ (absence) |
| Speed | No latency numbers. 50 DPM-Solver steps with CFG over a 96-frame sequence is heavy | READ + INFERRED |

**MacBook (Apple Silicon, Mac17,6, 128 GB unified memory):** capacity is not the blocker, since bf16 weights fit with room. The blockers are software: the repo is CUDA + FlashAttention only, there is no MPS or MLX path, and no quantized release. A port would be our work, for a model we could not ship. **Not feasible as released.** **INFERRED**

**photo-gallery (Linux x86_64):** feasible only if it has a 48 GB-class NVIDIA card or two 24 GB cards with a split. **Its GPU is not recorded in the docs we searched**; we have not verified it. The splat pipeline note says a GPU runner behind `SPLAT_RUNNER_URL` does not yet exist. Check `nvidia-smi` before anything else. **INFERRED**

**Licence consequence:** any use is limited to internal research or evaluation. We cannot ship it in a WeftOS product, a cog, a client deliverable or a paid Urth feature. Treat it like MASt3R (CC BY-NC-SA) in the S3 licence note. Counsel should read the exact text before even an internal client-facing demo. **READ** (terms) + **INFERRED** (consequence)

## 7. Fit in Urth and the BVH

| Layer | Fit | Why |
|---|---|---|
| BVH (ADR-056, ADR-078) | **None** | No geometry, no AABB, no object identity. Output cannot become a `WM_*` leaf |
| Urth L0-L3 (planet to site) | None | Needs OSM, DEM and capture, not video clips |
| Urth L4 appearance | Marginal | Could render a cosmetic preview ("what could this site look like"). image-blaster and Marble already cover that with a persistent splat |
| Urth L5 object | None | No instance segmentation or tracking |
| HNSW / `VectorRef` | Marginal | Its understanding side could caption frames, but a purpose-built embedder (S4, S6) fits `LANGUAGE_FEATURES` better and is cheaper |
| LeWM / ADR-090 | Watch | An action-free pixel-space dynamics prior. It has no camera or action conditioning, which S2/S8 models do |
| Graph Views F4 | Soft edges only | Captions as weak evidence, labelled non-metric, never promoted at F9 |
| Splat pipeline | None | No cameras, no depth. Does not touch COLMAP, VGGT or W1 |

Net: PixelUMM does not touch any of the open Urth residuals (live BVH publish, F9 promote, E1 region hierarchy, dual SpatialService). Same conclusion as the other S2 items: it would be appearance or a prior, never truth. **INFERRED**

## 8. Open questions

1. **Does the model card carry any carve-out** for derived outputs (generated clips) as distinct from the weights? Only the checkpoint terms were fetched, not the full licence text.
2. **Inference VRAM and speed** in bf16 for one 96-frame clip. Needs a measurement on a real NVIDIA box, not an estimate.
3. **What is photo-gallery's GPU**, and is a GPU runner planned?
4. **Is the generation expert fine-tunable for camera control**, or does the shared-attention design make it cheap to add PRoPE-style conditioning? The paper says camera control is not covered; whether it is straightforward is unknown.
5. **Does an encoder-free pixel interface help or hurt dense spatial tasks** (depth, correspondence)? No spatial benchmark appears in the results we read.
6. **Follow-up releases**: NVIDIA's Cosmos 3 (S2) is already an open omnimodal MoT with a clearer licence (OpenMDW-1.1). Compare the two before spending any time here.

## 9. Recommendation

1. **Record as S11, priority C (watch).** No code, no ticket, no adapter.
2. **Keep one pattern** in notes: hard token-level routing over shared attention. Reuse only if we design a single local model that must both caption and render.
3. **Re-check on three triggers:** a commercial or OpenMDW-style licence; an MLX/MPS or quantized release; a camera- or action-conditioned variant. Any one of these moves it to B.
4. **Do not** run it on client or NDA imagery, wire it into a WeftOS product path, or let its output reach BVH.
